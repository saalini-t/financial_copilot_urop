# Data Dictionary

Every field in `src/models/`. All models are Pydantic v2 `BaseModel`s — validation,
`model_dump_json()`, and `model_validate_json()` come from the library, nothing here
is hand-rolled serialization.

## User (`src/models/user.py`)

Generated by `simulations/generate_users.py` (Phase 3). Every user is fully
synthetic — no names, contact details, addresses, or real account numbers exist
anywhere in this schema. `catalogue_version`-style versioning: the generator
stamps `schema_version`, `generator_version`, and `dataset_version` into
`data/synthetic/users.json`'s `metadata` block so later experiments can state
exactly which dataset they ran against.

| Field | Type | Unit | Allowed values | Generation logic | Related fields |
|---|---|---|---|---|---|
| `user_id` | str | — | `^U\d{6}$`, e.g. `U000001` | Sequential index, zero-padded | — |
| `age` | int | years | 18–80 | `clip(normal(42, 13), 18, 80)`; forced to 18–30 for the `long_horizon` edge case | drives `investment_horizon_years`, `assets` |
| `monthly_income` | float | INR/month | > 0 | `clip(lognormal(ln(45000), 0.6), 8000, 400000)` — right-skewed, mimics real income spread | drives `monthly_expenses`, `assets`, `loans` |
| `monthly_expenses` | float | INR/month | ≥ 0 | `income × expense_ratio`, `expense_ratio = clip(normal(0.75, 0.18), 0.35, 1.3)` — the >1 tail is deliberate negative cash flow | correlated with `monthly_income`; drives `emergency_fund_target`, `savings` |
| `savings` | float | INR | ≥ 0 | `max(0, income − expenses) × accumulation_months + noise`; accumulation_months ~ U(0.5, 18) | must be ≤ `assets`; compared against `emergency_fund_target` |
| `assets` | float | INR | ≥ `savings` | `savings + income×12×0.15×(working_years/10) × lognormal(0, 0.8)` — scales with both income and age, heavy multiplicative noise | correlated with `monthly_income` and `age` |
| `liabilities` | float | INR | ≥ sum(`loans[].balance`) | `total_loan_balance + U(0, income×U(0,2))` — the extra term stands in for unmodeled revolving debt | ≥ sum of `loans[].balance` |
| `loans` | list[Loan] | — | 0–3 loans, types from `LoanType` | count ~ choice([0,1,2,3], p=[.35,.35,.2,.1]); types sampled without replacement from `{personal, education, vehicle, home}`; balance/rate ranges per type (see below) | feeds `liabilities`, `loan_interest_rates` |
| `loan_interest_rates` | list[float] (computed) | annual rate, e.g. 0.11 = 11% | derived from `loans[].interest_rate` | Not stored independently — a `@computed_field` reading `loans`, so it can never drift out of sync | mirrors `loans` |
| `risk_tolerance` | RiskTolerance | — | `low` / `moderate` / `high` | weighted propensity score: `0.5×horizon_score + 0.3×age_score + 0.2×U(0,1)`, thresholded — correlated but not determined by either input | correlated with `investment_horizon_years`, `age` |
| `investment_horizon_years` | int | years | > 0 (capped at 45) | `(60 − age) × U(0.6, 1.3)` if `age < 60`, else `U(1, 8)` — bounded so it's never incompatible with `age` | bounded by `age` |
| `emergency_fund_target` | float | INR | ≥ 0 | `monthly_expenses × multiple`, `multiple ~ choice([1,3,6,9], p=[.1,.45,.35,.1])` | correlated with `monthly_expenses`; compared against `savings` |
| `financial_goals` | list[FinancialGoal] | — | 0–4 goals, types from `GoalType` | count ~ choice([0,1,2,3], p=[.1,.4,.35,.15]); types sampled without replacement | drives `liquidity_requirements` |
| `liquidity_requirements` | float | INR | ≥ 0 | `savings×0.1 + Σ(per-goal liquidity bump)` — short-term purchase, home purchase, and emergency-fund goals contribute the most; retirement contributes least | driven by `financial_goals`, `savings` |
| `financial_literacy` | FinancialLiteracy | — | `low` / `medium` / `high` | `choice(["low","medium","high"], p=[.3,.45,.25])`, sampled independently of every other field so it never becomes an income proxy | none (independent by design) |

`Loan`: `loan_type` (`personal` / `education` / `vehicle` / `home`), `balance` (INR, ≥0),
`interest_rate` (annual rate, ≥0). Balance/rate ranges are type-specific synthetic
bands (e.g. home: 2–6× annual income at 7–11%; personal: ₹20k–500k at 11–24%) —
not modeled on any real lender's product.

`FinancialGoal`: `goal_type` (`short_term_purchase` / `home_purchase` /
`emergency_fund` / `retirement` / `education` / `other`), `target_amount` (INR, ≥0).

### Cross-field validation (enforced by the model, generation never repairs a violation)

- `assets ≥ savings`
- `liabilities ≥ Σ loans[].balance`

Both are `@model_validator` checks on `User` — a generated record that violates
either raises immediately, naming the `user_id`, rather than being silently fixed.

### Intentional edge cases

`simulations/generate_users.py` reserves ~5% of the dataset (minimum one per
category) for guaranteed, plausible edge cases: `very_low_savings`,
`high_expense_ratio`, `high_debt_to_income`, `no_loans`, `no_goals`,
`multiple_goals`, `very_high_liquidity_requirement`, `short_horizon`,
`long_horizon`, `insufficient_emergency_savings`. Each biases only the specific
sampling step needed for that category (e.g. `long_horizon` also biases `age`
young, so age and horizon never end up in an impossible combination) — see
`EDGE_CASE_CATEGORIES` and `_edge_case_for_index`. These exist so later
suitability, abstention, and personalization experiments have known-hard cases to
test against, not just the statistical middle of the distribution.

## Scenario (`src/models/scenario.py`)

Generated by `simulations/generate_scenarios.py` (Phase 3), which reads an
existing `data/synthetic/users.json` and references its user IDs unchanged —
scenarios are never generated for users that don't exist, and this script does
not invent one.

| Field | Type | Notes |
|---|---|---|
| scenario_id | str | sequential, e.g. `S000001` |
| scenario_type | ScenarioType | BUDGETING / DEBT_PRIORITIZATION / EMERGENCY_FUND / INVESTMENT_ALLOCATION / RETIREMENT |
| user_id | str | must reference an existing `User.user_id` |
| question | str | natural-language query, built from a fixed string template — never LLM-generated |
| relevant_user_attributes | dict | a literal snapshot of the referenced user's own field values (see `required_information`); every value here is copied from `User.model_dump()`, never invented |
| required_information | list[str] | `User` field names the decision needs — always equal to `relevant_user_attributes.keys()` |
| expected_decision_type | ScenarioType | currently always equal to `scenario_type` |

Each scenario type has 2-4 question templates, selected per (user, scenario
type) by a seeded `random.Random`. Templates span both straightforward
questions (quoting the user's real income/savings/loan figures) and
deliberately under-specified ones (e.g. "How much should I keep as an
emergency fund?", with no numbers stated) intended for later abstention and
personalization experiments. Debt scenarios for users with no loans, and
retirement scenarios for users with no `RETIREMENT`-type goal, deliberately
avoid citing a number that doesn't exist in the profile rather than fabricating
one — see `_debt_templates` / `_retirement_templates` in the generator.

## Candidate / CandidateEvaluation (`src/models/candidate.py`)

`Candidate`: candidate_id, scenario_type, parameters (dict), catalogue_version
(defaults to `CATALOGUE_VERSION`, currently `"1.0.0"`).

`CandidateEvaluation` — one candidate's score against a specific user + scenario:

| Field | Type | Notes |
|---|---|---|
| candidate_id | str | |
| feasible | bool | required inputs available |
| hard_constraint_violations | list[str] | rule IDs that fired |
| goal_alignment_score | float [0,1] | |
| suitability_score | float [0,1] | 1 = fully suitable / lowest risk |
| financial_objective_score | float [0,1] | |
| liquidity_score | float [0,1] | only ranking-relevant for liquidity-relevant scenarios |
| total_score | float | composite score, confidence only — never used for ranking |
| rejection_reasons | list[str] | |

`get_candidates(scenario_type)` returns the frozen catalogue in fixed order.
`catalogue_order(scenario_type, candidate_id)` returns the tie-break-of-last-resort index.

## AuditArtifact / CommunicationArtifact (`src/models/artifacts.py`)

`AuditArtifact` — the structured source of truth:
retrieved_evidence (list[EvidenceItem]), tool_traces (list[ToolTraceEntry]),
constraints (list[ConstraintRecord]), candidate_evaluations (list[CandidateEvaluation]),
rejected_candidates (list[str]), assumptions (list[str]), final_decision (Decision),
configuration (str, the config_name), timestamp (datetime).

`CommunicationArtifact` — the rendering shown to the user:
recommendation (str), explanation (str), citations (list[str]),
numerical_claims (list[NumericalClaim]), constraint_claims (list[str]),
assumptions (list[str]).

`EvidenceItem`: source_id, text, relevance_score [0,1].
`ToolTraceEntry`: tool_name, tool_version, inputs (dict), outputs (dict).
`ConstraintRecord`: rule_id, description, binding (bool), violated_by (list[str]).
`NumericalClaim`: claim (str), value (float), source_field (str — pointer into the
audit artifact this claim must match; used by Faithfulness Test E).

## ExperimentConfig (`src/config.py`)

config_name, description, catalogue_version, ground_truth_engine_version,
random_seed, min_confidence [0,1], tie_epsilon (>0), scoring_weights
(ScoringWeights: w_goal, w_risk, w_obj, w_liq), modules (ModuleToggles: use_rag,
use_tools, use_personalization, use_constraints, use_candidate_catalogue),
explanation_type, model_id, temperature, prompt_version, retrieval (dict),
tool_config (dict) — the last three added in Phase 6A so no agent
implementation hard-codes them.

## ExperimentInput / ExecutionMetadata (`src/models/experiment.py`, Phase 6A)

`ExperimentInput` — common to all four configurations, built only by
`build_experiment_input(scenario)`:
user_id, scenario_id, scenario_type, question, relevant_user_attributes (dict),
required_information (list[str]).

`ExecutionMetadata` — never contains API keys or secrets:
configuration (ConfigurationName), model_identifier, prompt_version,
dataset_version, scenario_dataset_version, ground_truth_version,
experiment_seed, retrieval_configuration (dict), tool_configuration (dict).

`ConfigurationName`: baseline / rag / personalized / full_copilot.
`make_experiment_id(configuration, scenario_id, run_id)`: deterministic string
join, used as `ExperimentOutput.experiment_id`.

## ExperimentOutput (`src/models/response.py`, Phase 6A)

Returned by every `src/agents/*.py` `run()` function:
experiment_id, configuration, scenario_id, user_id, decision (str),
abstention (bool), abstention_reason (AbstentionReason | None — required iff
abstention=True), explanation (str), evidence (list[Evidence]), confidence
(Confidence), artifacts (list[Artifact]), execution_metadata (ExecutionMetadata).

`AbstentionReason` (experiment-level; distinct from `src.decision.ranking.AbstentionReason`,
the Phase 5 ground-truth oracle's own narrower set): MISSING_REQUIRED_INFORMATION,
NO_VALID_CANDIDATE, TOOL_FAILURE, EVIDENCE_UNAVAILABLE, UNSUPPORTED_SCENARIO,
LOW_CONFIDENCE, OTHER.

`Confidence`: available (bool), value (float [0,1] | None — required iff
available=True, forbidden otherwise), method (str), reason (str | None).

## Artifact / Evidence (`src/models/artifacts.py`, Phase 6A additions)

`Artifact` — a generic, configuration-agnostic record of one execution step,
never chain-of-thought: artifact_type, source, input (dict), output (dict),
execution_id, provenance (dict).

`Evidence` — a structured citation, distinct from the fuller-copilot-specific
`EvidenceItem` above: evidence_id, source_type, source_reference (must point
to something real, never fabricated), excerpt_or_fact, relevance [0,1],
provenance (dict).
